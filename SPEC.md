# fishjam_client behavioral specification

This document is the contract every module of `fishjam_client` is built and tested against. It describes
observable behavior: what goes over the wire, in what order, what the SDK emits to the app, and how it
reacts to failures. Where this SDK intentionally behaves differently from the Fishjam web SDK, the
difference is listed in [§22](#22-deviations-from-the-web-sdk).

Golden message sequences for the scenarios below live in `test/fixtures/*.json`
(format: [§23](#23-golden-fixtures)). When this document and a fixture disagree, fix one of them in the same
change.

Conventions:

- "kbps" always means **1024 bits per second** (see [§13](#13-bandwidth)).
- "Send X" means: encode a `PeerMessage` carrying X and write it to the socket as one binary frame.
- Section numbers are referenced from code comments as `SPEC §N`.

## 1. Glossary

| Term | Meaning |
|---|---|
| Session | One authenticated socket plus one peer connection. A reconnect starts a new session. |
| Endpoint | Anything in a room that the server reports: a **peer** (another client) or a **component** (server-side producer such as a recording or a stream ingest). |
| Local track | A track this client publishes. Its id is `<localPeerId>:<uuid v4>`, generated by the SDK. |
| Remote track | A track published by another endpoint, identified by the id the server sends. |
| Negotiation | One offer/answer cycle: `offerData` → `sdpOffer` → `sdpAnswer`. |

## 2. Wire protocol

### 2.1 Transport

- URL: `<url>/socket/peer/websocket`. A single trailing `/` on `<url>` is not duplicated.
- Every frame in both directions is **binary** and contains exactly one `fishjam.PeerMessage`.
- Text frames from the server are ignored (logged at debug level).
- The server pings every 30 s. The client additionally sends its own pings (interval 15 s) and treats a
  missing pong within one interval as a connection loss (retryable, [§6](#6-reconnection)).

### 2.2 Messages

| Direction | `PeerMessage.content` | Used for |
|---|---|---|
| client → server | `authRequest{token, sdkVersion}` | first frame after the socket opens |
| server → client | `authenticated{roomType, sdkDeprecation}` | authentication succeeded |
| client → server | `peerMediaEvent` | all signaling after authentication |
| server → client | `serverMediaEvent` | all signaling after authentication |
| client → server | `rtcStatsReport{data}` | periodic statistics ([§17](#17-statistics-reporting)) |
| either | `mediaEvent` (legacy JSON string) | never sent; ignored when received |

`sdkVersion` is exactly `flutter-<package version>`, e.g. `flutter-0.31.0`. The package version follows the
web SDK release train (lockstep), because the server classifies versions older than its own minor minus four
as unsupported regardless of language.

### 2.3 Metadata JSON

Every `*_json` / `metadataJson` field the client sends **must be valid JSON**. An empty string is invalid and
makes the server drop the whole event (for `sdpOffer`, the whole negotiation). Rules:

- A Dart value is encoded with `jsonEncode`. `null` (absent metadata) is encoded as the JSON literal `null`.
- So `connect.metadataJson` for absent peer metadata is the string `"null"`, never `""`.
- Values received from the server are decoded with `jsonDecode`; an empty string decodes to `null`, an
  undecodable string is logged and treated as `null` (never throws out of the event loop).
- Endpoint metadata received from the server is an object `{"peer": <peer metadata>, "server": <server metadata>}`.
  It is exposed as `Metadata(peer:, server:)`. If the value is not an object of that shape, `peer` holds the
  whole decoded value and `server` is `null`.

## 3. Connection lifecycle

### 3.1 Status

`FishjamClient.status` is one of:

```
idle ──connect()──▶ connecting ──authenticated──▶ authenticated ──connected──▶ joined
  ▲                    │                              │                          │
  │                    └───────── terminal close / leave() ──────────────────────┤
  │                                                                              │
  └──────────────────────────── disconnected ◀───── retries exhausted ◀─ reconnecting
                                                                            ▲   │
                                              retryable loss while joined ──┘   └─ joined (Reconnected)
```

| Status | Meaning |
|---|---|
| `idle` | Never connected. |
| `connecting` | Socket opening or `authRequest` sent, waiting for `authenticated`. |
| `authenticated` | `connect` media event sent, waiting for `connected`. |
| `joined` | `connected` received; media can flow. |
| `reconnecting` | A retryable loss happened; a new session is being set up ([§6](#6-reconnection)). |
| `disconnected` | Terminal. The client can be connected again with `connect()`. |

### 3.2 `connect()`

1. Emit nothing yet; set status `connecting`; open the socket.
2. On open: send `authRequest`.
3. On `authenticated`: record the room type ([§20](#20-audio-only-rooms)); handle `sdkDeprecation`
   (`STATUS_DEPRECATED` → warning log, `STATUS_UNSUPPORTED` → error log, otherwise nothing); emit
   `AuthSucceeded`; send `connect{metadataJson}`; status `authenticated`.
4. On `connected`: build the local peer and the remote endpoint snapshot ([§14](#14-remote-endpoints-and-tracks)),
   start statistics reporting, status `joined`, emit `Joined(peerId, peers, components)`.
   `connect()` completes successfully.
5. `connect()` **always settles**. It completes with an error if the session ends before `Joined`:
   - auth close reason → `AuthException(reason)` (and `AuthFailed` is emitted),
   - join close reason → `JoinException(reason)` (and `JoinFailed` is emitted),
   - any other close or socket failure before `Joined` → `ConnectionException(code, reason)`.
   Reconnection is **not** attempted for failures before the first `Joined`.
6. Calling `connect()` while not `idle`/`disconnected` throws `StateError`.

### 3.3 `leave()`

1. Send `peerMediaEvent.disconnect` **before** tearing anything down (it must reach the server).
2. Cancel reconnection, stop stats, close data channels, close the peer connection, release the local streams
   the SDK created (the app's media tracks are taken out first, not stopped), close the socket with code 1000.
3. Status `disconnected`; emit `Disconnected(DisconnectReason.left)` exactly once.
4. Pending track operations fail with `StateError('disconnected')`.

### 3.4 Server-initiated end

- `endpointRemoved` whose `endpointId` is the local peer: tear down as in §3.3 steps 2–4 (no `disconnect`
  is sent), emit `Disconnected(DisconnectReason.peerRemoved)`.
- `serverMediaEvent.error{message}`: emit `ServerError(message)`, then behave as `leave()` but emit
  `Disconnected(DisconnectReason.serverError)`.
- Socket close: classified by [§4](#4-close-reasons).

## 4. Close reasons

The close reason string is normalized with `trim().toLowerCase()` before matching.

| Normalized reason | Class | Effect |
|---|---|---|
| `missing token`, `invalid token`, `expired token`, `room not found`, `peer not found` | **auth error** | emit `AuthFailed(reason)`, terminal |
| `reached peers limit`, `node not found`, `invalid sdk version` | **join error** | emit `JoinFailed(reason)`, terminal (`node not found` is terminal even though the server sends it with code 1011, as in the web SDK) |
| `peer removed`, `room stopped`, `new client connected as this peer` | **session ended** | terminal, no error event; `Disconnected(peerRemoved / roomStopped / replacedByNewClient)` |
| `unauthenticated`, `malformed protobuf` | **protocol error** | terminal, logged as error (indicates an SDK bug) |
| anything else (including empty reason, abnormal closure, pong timeout, network loss) | **retryable** | reconnect if joined and enabled, else terminal |

A terminal close emits exactly one `Disconnected(reason)`; there is no separate "session ended" event. The
`DisconnectReason` values are: `left` (§3.3), `peerRemoved`, `roomStopped`, `replacedByNewClient`, `serverError`
(§3.4), `authError`, `joinError`, `protocolError`, `connectionLost` (retryable loss with reconnection disabled
or before the first `Joined`), `reconnectionFailed` (§6). `room not found` is an auth error only (it is not
reported twice).

## 5. Outgoing message queue

All client → server messages go through a single ordered queue in front of the socket.

- **Bypass** (sent immediately on the current socket, never queued): `authRequest`, and the peer media events
  `connect`, `renegotiateTracks`, `sdpOffer`, `candidate`. These belong to the session being set up.
- **Queued**: every other peer media event and `rtcStatsReport`.
- While status is `reconnecting`, queued messages are held. Otherwise the queue is flushed immediately in FIFO
  order.
- The queue is flushed when the reconnection completes (`Reconnected`) and **cleared** when it fails or the
  client leaves. A held queue can never outlive the reconnection attempt.
- Writing to a closed socket is a no-op (logged at debug level).

## 6. Reconnection

Configuration (`ReconnectConfig`): `maxAttempts` (default 3), `initialDelay` (default 500 ms), `delay`
(default 500 ms), `addTracksOnReconnect` (default false). `ReconnectConfig.disabled` turns it off. Reconnect is
enabled with defaults unless configured otherwise.

States: `idle`, `reconnecting`, `failed`.

| From | Trigger | Action | To |
|---|---|---|---|
| idle (joined) | retryable loss: retryable close, socket error, pong timeout, peer connection `failed`, ICE `failed` | snapshot local peer metadata (`peer` part) and local tracks; emit `ReconnectionStarted`; schedule attempt 1 | reconnecting |
| reconnecting | attempt timer fires | tear down old session silently (no `Disconnected`); start a new session with the snapshot metadata | reconnecting |
| reconnecting | retryable loss in the new session before `connected` (including a new session that cannot be started at all) | schedule next attempt if attempts remain | reconnecting |
| reconnecting | retryable loss, no attempts left | clear queue; emit `ReconnectionFailed`, then `Disconnected(DisconnectReason.reconnectionFailed)` | failed |
| reconnecting | terminal close (auth/join/session ended/protocol) | cancel timer; clear queue; emit the matching error event and `Disconnected` | failed |
| reconnecting | `connected` | emit `Joined`; if `addTracksOnReconnect`, re-add every snapshotted track whose media track is still live (skip, do not abort on, ended or muted tracks); emit `LocalTrackRemoved(oldTrackId)` for every snapshotted track that is not re-added (ended, muted, or its re-add failed); when all re-adds settled (success or failure): flush queue, emit `Reconnected`, reset attempt counter | idle |
| any | `leave()` | cancel timer; clear queue | idle |

- Delay of attempt `n` (1-based) is `initialDelay + (n - 1) * delay`.
- Only one attempt timer exists at a time; triggers while a timer is pending are ignored.
- Failures before the first `Joined` of a `connect()` call never start reconnection ([§3.2](#32-connect)).
- A re-added track gets a **new** track id; `LocalTrackAdded` is emitted for it.
- A **muted** track (no media track) is not re-added: there is nothing to publish. The app is told with
  `LocalTrackRemoved` and adds the track again when it unmutes.

## 7. Media event processing

- Server media events are processed **strictly one at a time, in arrival order**. Handling of event N+1 starts
  only after every asynchronous step of event N completed (e.g. `setRemoteDescription` of an answer finishes
  before the next `offerData` is handled).
- Events received before `connected` are dropped (logged). `connected` itself is processed in order.
- A failure while handling one event is logged and does not stop the processing of later events.
- References to unknown endpoints or tracks are **logged and ignored**; they never throw and never corrupt
  local state.
- Events about the local endpoint (`endpointId == localPeerId`) in `endpointAdded`, `endpointUpdated`,
  `tracksAdded`, `tracksRemoved`, `trackUpdated` are ignored without any state change.

## 8. Negotiation

A single explicit state machine owns negotiation. No other flag decides whether a negotiation is in progress.

### 8.1 States

| State | Meaning |
|---|---|
| `idle` | No negotiation in flight. Commands may start. |
| `requested` | Client sent `renegotiateTracks`, or a remote `tracksAdded` announced a server-initiated cycle; waiting for `offerData`. |
| `offerSent` | `sdpOffer` sent; waiting for `sdpAnswer`. |

`offerData` handling (sync transceivers, drain batch, create offer, set local description) runs inside the
serialized event handler ([§7](#7-media-event-processing)), so it is not a separate observable state.

### 8.2 Transitions

| From | Event | Action | To |
|---|---|---|---|
| idle | negotiating command starts (add track, remove track, create data channels) | apply command; send `renegotiateTracks` | requested |
| idle | `tracksAdded` from a remote endpoint | — | requested |
| idle / requested | `offerData` | create the peer connection if needed ([§8.4](#84-peer-connection)); sync receive transceivers ([§9](#9-receive-transceiver-sync)); drain the batch ([§8.3](#83-command-queue)); `createOffer`; `setLocalDescription`; build `sdpOffer` ([§10](#10-sdpoffer-contents)); mark every local track included as `offered`; send `sdpOffer` | offerSent |
| offerSent | `offerData` | logged as unexpected; handled like the row above (server abandoned the previous cycle) | offerSent |
| requested | negotiating command starts | apply command; **do not** send another `renegotiateTracks` (rides the pending cycle) | requested |
| offerSent | `sdpAnswer` | record mids ([§10.2](#102-applying-the-answer)); `setRemoteDescription`; mark offered tracks `negotiated`; send deferred metadata updates ([§11.6](#116-metadata)); complete the commands of this cycle | idle, then start next command |
| idle / requested | ICE connection state `disconnected` | send `renegotiateTracks` (logged as warning) | requested |
| offerSent | ICE connection state `disconnected` | remember one restart request; when the cycle ends, send `renegotiateTracks` | offerSent |
| any | `sdpAnswer` outside `offerSent` | logged and ignored | unchanged |
| requested / offerSent | the cycle fails: `createOffer`, `setLocalDescription` or `setRemoteDescription` throws or takes longer than 10 s | fail the cycle's commands with the error; unregister the tracks whose `addTrack` failed and remove their senders; emit `ConnectionError(message)`, a retryable loss ([§6](#6-reconnection)) | idle |

The server itself queues a `renegotiateTracks` received during a cycle, so it may start a new cycle with an
`offerData` that is not preceded by `tracksAdded`. `offerData` in `idle` is therefore normal.

A failed cycle cannot be recovered within the session: the server ends its cycle only when it receives an
`sdpOffer`, and a failed `setRemoteDescription` leaves the peer connection's descriptions inconsistent. So it is
handled as a connection failure and the session is replaced. Failures caused by tearing the session down are
cancellations: nothing is logged as an error and no `ConnectionError` is emitted.

### 8.3 Command queue

Commands are user operations that touch the peer connection's sender set:

| Command | Needs negotiation | Batchable | Completes when |
|---|---|---|---|
| add track | yes | yes | the `sdpAnswer` of the cycle that carried it was applied |
| create data channels | yes | yes | both channels are open ([§16](#16-data-channels)) |
| remove track | yes | no | the `sdpAnswer` of the cycle that carried it was applied |
| replace track (incl. mute/unmute) | no | no | `replaceTrack` on the sender resolved |

Rules:

1. Commands run in FIFO order. A command starts only in `idle`.
2. In `requested`, queued **batchable** commands at the head of the queue start immediately (no new
   `renegotiateTracks`). On `offerData`, batchable commands at the head of the queue are drained into the offer
   being built. Draining stops at the first non-batchable command.
3. Validation runs when the command starts. A failing command completes with its error and does not affect
   the other commands of the same batch.
4. Several `addTrack` calls made back to back before `offerData` produce **exactly one** `renegotiateTracks`
   and **one** `sdpOffer` containing all of them.
5. `addTrack` called after the `sdpOffer` was sent waits for the next cycle and triggers its own
   `renegotiateTracks` when the queue reaches it.
6. Teardown (leave, removal, reconnection) fails every pending and in-flight command with
   `StateError('disconnected')`.

### 8.4 Peer connection

- Created lazily, on the first `offerData` or `createDataChannels()`, whichever comes first, with the ICE
  servers from `connected` (`urls`, `username`, `credential`), bundle policy `max-bundle`, ICE transport
  policy `all`.
- On creation, every already registered local track is added as a send transceiver ([§11.1](#111-add-track)).
- Local ICE candidates are sent as `candidate{candidate, sdpMLineIndex, sdpMid, usernameFragment}`. A null
  candidate (end of gathering) is not sent. Remote candidates are added with `addIceCandidate`; failures are
  logged.
- Connection state `failed` or ICE connection state `failed` emits `ConnectionError(message)` and is a
  retryable loss ([§6](#6-reconnection)).
- A new session always creates a new peer connection; the old one is closed.

## 9. Receive transceiver sync

On every `offerData{tracksTypes{audio, video}}`, the client makes the number of **live receive transceivers**
per kind equal the server's numbers. A transceiver is a live receive transceiver when its direction is
`recvonly` and its current direction is not `stopped`; its kind is its receiver track kind.

1. Count live receive transceivers per kind.
2. If there are more than requested, stop the excess, choosing transceivers with no `mid` first.
3. If there are fewer, add `recvonly` transceivers: first all missing **video**, then all missing **audio**.
4. Negative deltas never throw.

## 10. `sdpOffer` contents

### 10.1 Building the offer

Built **after** `setLocalDescription` (so new transceivers have mids):

- `sdp`: the local description SDP.
- `trackIdToMetadataJson`: every local track → JSON of its current metadata ([§2.3](#23-metadata-json)).
- `trackIdToBitrates`: every local track → `TrackBitrates{trackId, variantBitrates}` ([§13.5](#135-reported-bitrates)).
- `midToTrackId`: union of
  1. every transceiver with a non-null `mid` whose sender has a track → the local track owning that media
     track (matched by media track id), and
  2. every local track that already has a mid from a previous answer (keeps muted tracks, whose sender has no
     media track, mapped).
  A transceiver whose sender track belongs to no local track is skipped and logged (never throws).

### 10.2 Applying the answer

For each `mid → trackId` in `sdpAnswer.midToTrackId`: if `trackId` is a local track, store the mid on it; if
it is a remote track, store the mid on it (used to resolve `onTrack`, [§14.3](#143-track-ready)).

## 11. Local tracks

### 11.1 Add track

`addTrack(track, {metadata, simulcastConfig, maxBandwidth}) → Future<String trackId>`

1. Throws `TrackTypeError` synchronously for a video track in an audio-only room ([§20](#20-audio-only-rooms)).
2. Fails with `StateError` before `Joined`.
3. Resolves the bandwidth limit ([§13](#13-bandwidth)) **before** registering; an invalid limit (simulcast map
   for a non-simulcast track) fails without registering anything.
4. Fails when the media track is already published.
5. Registers the track (id `<localPeerId>:<uuid>`), negotiation status `pending`. If the peer connection
   exists, adds a send transceiver: audio → `sendonly`, streams `[stream]`, no encodings; video non-simulcast
   → `sendonly`, one encoding `{active: true, maxBitrate}`; video simulcast → [§12](#12-simulcast).
6. Completes after the answer; emits `LocalTrackAdded(trackContext)`.

Streams (lip sync): tracks whose metadata type is `camera` or `microphone` share one local stream; tracks of
type `screenShareVideo` or `screenShareAudio` share another; any other track gets its own stream. Streams are
created with `RtcAdapter.createLocalMediaStream` and passed in `TransceiverInit.streams`.

Sender-only operations (§11.4, §11.5) are not queued commands: they act on the sender immediately and fail with
`StateError` when the track has no sender yet (before its first negotiation).

### 11.2 Remove track

Removes the sender from the peer connection (`removeTrack`), unregisters the track, triggers negotiation.
Completes after the answer; emits `LocalTrackRemoved(trackId)`. Unknown id → `ArgumentError`.

### 11.3 Replace, mute, unmute

`replaceTrack(trackId, newTrack?)` replaces the sender track without negotiation.

| Old track | New track | Action |
|---|---|---|
| present | `null` | **mute**: emit `LocalTrackMuted(trackId)` |
| `null` | present | **unmute**: send `unmuteTrack{trackId}`, emit `LocalTrackUnmuted(trackId)` |
| otherwise | | **replace** |

Then `sender.replaceTrack(newTrack)`. On failure the previous track is restored, the opposite mute/unmute
event is emitted and the call fails with the sender's error. On success emit `LocalTrackReplaced(trackId, track)`.
Unknown id, or a media track already published by another local track (same rule as §11.1) → `ArgumentError`,
nothing emitted. Before the track has a sender, only the stored track changes (events as above).

### 11.4 Encodings (sender variants)

`enableTrackEncoding` / `disableTrackEncoding(trackId, variant)`: find the sender encoding whose rid maps to
the variant (`l`, `m`, `h`), set `active`, `setParameters`, then send `enableTrackVariant` /
`disableTrackVariant{trackId, variant}` and emit `LocalTrackEncodingEnabled` / `LocalTrackEncodingDisabled`
(the correct one for each operation). The track's `simulcastConfig` enabled/disabled variants follow. Missing
encoding → `ArgumentError`.

### 11.5 Bandwidth

`setTrackBandwidth(trackId, limit)` and `setEncodingBandwidth(trackId, variant, kbps)`: resolve
([§13](#13-bandwidth)), apply to sender encodings with `setParameters`, store the resolved value on the track,
send `trackBitrates{trackId, variantBitrates}` for the whole track, emit `LocalTrackBandwidthSet(trackId,
limit)` / `LocalTrackEncodingBandwidthSet(trackId, variant, kbps)` — each exactly once.

### 11.6 Metadata

- `updatePeerMetadata(m)`: store, send `updateEndpointMetadata{metadataJson}`, emit
  `LocalPeerMetadataChanged(m)`.
- `updateTrackMetadata(trackId, m)` by the track's negotiation status:
  - `pending` (not yet offered): store only; the coming `sdpOffer` carries it.
  - `offered` (in the `sdpOffer` in flight): store; after the answer is applied, send one
    `updateTrackMetadata` with the **latest** value.
  - `negotiated`: store, send `updateTrackMetadata{trackId, metadataJson}`.
  `LocalTrackMetadataChanged(trackId, m)` is emitted when the update is sent; a `pending` track emits nothing
  (the coming offer carries the value and `LocalTrackAdded` reports it), as in the web SDK.

## 12. Simulcast

A simulcast video track gets three send encodings, ordered low → high:

| rid | Variant | `scaleResolutionDownBy` | `active` |
|---|---|---|---|
| `l` | low | 4 | low ∈ enabledVariants |
| `m` | medium | 2 | medium ∈ enabledVariants |
| `h` | high | 1 (omitted) | high ∈ enabledVariants |

Each encoding's `maxBitrate` is its resolved layer limit in bps (`kbps × 1024`), or unset when the limit is 0.
On the receive side, a missing rid means `h`.

## 13. Bandwidth

Limits are given in kbps (×1024 to get bps).

### 13.1 Caps

| | cap (kbps) |
|---|---|
| single stream video | 1500 |
| simulcast low / medium / high | 150 / 500 / 1500 |

### 13.2 Resolving a single-stream video limit

`0` or negative → the cap. Above the cap → the cap, with a warning log. Otherwise unchanged. A per-variant map
→ `ArgumentError` ("a non-simulcast track expects a single bandwidth limit").

### 13.3 Resolving a simulcast video limit

- A map: every variant (low, medium, high) is present in the result; a missing, 0 or negative entry becomes
  the variant's cap; values above the cap are clamped with a warning.
- A number `> 0`: split proportionally to pixel count — with scales `4, 2, 1` the weights are `1 : 4 : 16`;
  `x = budget_bps / 21`, layer `i` gets `x × weight_i` bps, converted back with `round(bps / 1024)` kbps — then
  resolved like a map (so each layer is clamped to its cap). Example: 1500 → 71 / 286 / 1143; 2100 → 100 /
  400 / 1500.
- `0` or negative: every layer gets its cap.

### 13.4 Audio

Audio tracks are added without a limit (`0`). `setTrackBandwidth` on an audio track applies the given number
as is; a map → `ArgumentError`. `setEncodingBandwidth` on audio is an `ArgumentError` (audio has no layers).

### 13.5 Reported bitrates

`variantBitrates` for `trackIdToBitrates` and `trackBitrates`:

- single limit `n`: `[{variant: VARIANT_UNSPECIFIED, bitrate: n × 1024}]`; when `n == 0`, the default:
  **50 000 bps** for audio, **1 536 000 bps** (1500 × 1024) for video.
- simulcast map: one entry per variant in low, medium, high order, `bitrate = kbps × 1024`.

### 13.6 Applying to sender encodings

- Single number on a sender: if the sender has no encodings, use one unlimited encoding; otherwise split the
  number across the existing encodings proportionally to `(scale₀ / scaleᵢ)²` (scale defaults to 1); 0 removes
  `maxBitrate`.
- Map on a simulcast sender: each encoding with a rid gets `maxBitrate = map[variant] × 1024`, unset when 0.
- `setEncodingBandwidth`: the matching rid's `maxBitrate = kbps × 1024`; 0 removes it.

## 14. Remote endpoints and tracks

### 14.1 Endpoints

- Endpoint type `webrtc` or `exwebrtc` → `Peer`. `recording`, `hls`, `file`, `rtsp`, `sip` → `Component`.
  Any other type is ignored (logged at debug level), including its tracks.
- `connected` provides the initial snapshot: the local peer (metadata) and every other endpoint with its
  tracks. They are delivered in `Joined` only, in the order the server listed them; no
  `PeerJoined`/`TrackAdded` is emitted for them.
- `endpointAdded` carries no endpoint type, so the new endpoint is always a `Peer` of type `exwebrtc` →
  `PeerJoined`. Components are therefore only learned from `connected`.
- `endpointUpdated` → store metadata, `PeerUpdated` / `ComponentUpdated`. `endpointRemoved` → `TrackRemoved`
  for each of its tracks, then `PeerLeft` / `ComponentRemoved`.

### 14.2 Tracks

- `tracksAdded{endpointId, trackIdToTrack}` → for each new track: create a `RemoteTrack` (metadata,
  simulcast config, no media yet), emit `TrackAdded`. A track id that is already known is updated in place
  (metadata, simulcast config) without a second `TrackAdded`. A track id owned by another endpoint is logged and
  ignored.
- `tracksRemoved{endpointId, trackIds}` → remove, emit `TrackRemoved` for each known id.
- `trackUpdated{endpointId, trackId, metadataJson}` → store, emit `TrackUpdated`.
- Remote track metadata is decoded into `TrackMetadata` when it has the shape
  `{type, paused, displayName?}`; the raw decoded value is always available.

### 14.3 Track ready

On the peer connection's `onTrack(track, streams, transceiver)`: find the remote track whose mid equals the
transceiver mid. Unknown mid → logged and ignored. Otherwise attach the media track and `streams.first`
(when present), set the kind from the media track, emit `TrackReady`. `TrackReady` always follows
`TrackAdded` for the same id.

### 14.4 Variants (receiving simulcast)

- `setTargetTrackEncoding(trackId, variant)`: validate **before** storing — the track must be known and
  simulcast and the variant must be in its enabled variants, otherwise `ArgumentError` and nothing is sent. Then send
  `setTargetTrackVariant{trackId, variant}` and emit `TargetTrackEncodingRequested(trackId, variant)`.
- `trackVariantSwitched{trackId, variant}` → set `encoding`, emit `TrackEncodingChanged`. `encodingReason`
  stays `null` (the server does not provide one).
- `trackVariantEnabled` / `trackVariantDisabled` → move the variant between the track's enabled and disabled
  variant lists, emit `TrackVariantsChanged`.

### 14.5 Voice activity

`vadNotification{trackId, status}`: `STATUS_SPEECH` → `speech`, `STATUS_SILENCE` → `silence`, emit
`VoiceActivityChanged`. Unspecified status → logged and ignored. The initial status of a remote track is
`silence`.

## 15. Peers in events

All public events carry immutable snapshots (`Peer`, `Component`, `RemoteTrack`, `LocalTrack`) taken at the
moment of emission. Getters (`remotePeers`, `remoteComponents`, `remoteTracks`, `localPeer`) return current
snapshots.

## 16. Data channels

- Exactly two channels, created on the peer connection by `createDataChannels()`:
  - label `reliable`, `ordered: true`;
  - label `lossy`, `ordered: false`, `maxRetransmits: 0`.
  The server rejects any other label.
- `createDataChannels()` is a batchable negotiating command ([§8.3](#83-command-queue)); it is a no-op when both
  channels are already open, and completes when both are open (`DataChannelsReady` is emitted once). It fails
  with the error if either channel errors or closes before opening (`DataChannelsError` emitted).
- `publishData(bytes, {reliable})`: throws `StateError` when the channel does not exist or is not open.
  Otherwise sends one binary message: `ChannelMessage{source: <localPeerId>, destinations: ["*"],
  binary{data: bytes}}` encoded as protobuf.
- Incoming messages are decoded as `ChannelMessage`; when `binary` is set, `binary.data` is delivered to
  `dataStream(reliable: <channel == reliable>)` subscribers. Text messages are converted to UTF-8 bytes first.
  Undecodable messages are logged and dropped.
- `dataStream(...)` may be subscribed before the channels exist; subscriptions survive reconnection. Channels
  are closed on teardown, which fails a pending `createDataChannels()` with `StateError('disconnected')`
  without emitting `DataChannelsError` (also when the engine fails the command with
  `StateError('disconnected')`). After a failure, `createDataChannels()` may be called again. Disposing the
  client ends every `dataStream`.

## 17. Statistics reporting

- Every 10 s while `joined`, the client calls `getStats()` on the peer connection and sends
  `rtcStatsReport{data}` (queued, [§5](#5-outgoing-message-queue)).
- `data` is a JSON object mapping each report id to the report's fields (including `id`, `type`, `kind`,
  `timestamp`), containing only reports of type `inbound-rtp` or `outbound-rtp`. Values JSON cannot represent
  (`NaN`, infinities) are sent as `null`. A report whose `getStats()` is still running at teardown is dropped.
- The timer starts on `Joined` (every session) and stops on teardown. A failing `getStats()` skips the tick.

## 18. Local audio level

`getLocalTrackAudioLevel(trackId) → Future<double?>`: `null` for unknown tracks, tracks without a sender,
or when stats fail. Otherwise the `audioLevel` (0.0–1.0) of the first `media-source` stats report of kind
`audio` from `sender.getStats()`, or `null` if none.

## 19. Livestreams (WHIP / WHEP)

Plain HTTP, no Fishjam socket.

- **Publish (WHIP)** `publishLivestream(stream, url, token)`: requires at least one audio or video track
  (otherwise `ArgumentError`). Peer connection with `max-bundle`; one `sendonly` transceiver for the first video
  and the first audio track. Create offer, set local description, wait for ICE gathering to complete, then
  `POST url` with `Content-Type: application/sdp`, `Authorization: Bearer <token>`, body = offer SDP. Expect
  `201` with the answer SDP and a `Location` header (resolved against `url`). Set remote description.
  ICE gathering waits at most `iceGatheringTimeout` (default 3 s); on timeout the offer is sent with the
  candidates gathered so far.
- **Receive (WHEP)** `receiveLivestream(url, {token})`: `recvonly` video and audio transceivers, same exchange
  (bearer header only when a token is given). Completes when the first remote stream arrives; if the
  connection fails or closes first, or no stream arrives within `firstStreamTimeout` (default 10 s) after the
  answer, it stops (as below) and fails with `unknownError`.
- **Stop**: `DELETE <Location>` with the same bearer header, then close the peer connection. A failed DELETE
  is logged; the peer connection is closed regardless. Without a `Location` header nothing is deleted. Stop is
  idempotent. A failure after a successful POST (e.g. the answer cannot be applied) stops the same way.
- Status mapping for the POST: `401` → `LivestreamError.unauthorized`, `404` → `streamNotFound`,
  `409` (publish only) → `streamerAlreadyConnected`, anything else non-2xx, a network error or a WebRTC
  failure → `unknownError` (with the original error as `cause`).

## 20. Audio-only rooms

When `authenticated.roomType` is `ROOM_TYPE_AUDIO_ONLY`, `addTrack` with a video track throws
`TrackTypeError` synchronously and nothing is sent.

## 20a. Public types and the WebRTC boundary

- The public API uses `flutter_webrtc` types: `addTrack(MediaStreamTrack, …)`,
  `replaceTrack(trackId, MediaStreamTrack?)`, `getStatistics([MediaStreamTrack?])`, and the `track` / `stream`
  getters of `LocalTrackContext`, `RemoteTrackContext` and `LocalTrackReplaced` return `MediaStreamTrack?` /
  `MediaStream?`, ready for `RTCVideoView`. Livestream functions take and return `MediaStream`.
- Internally every module works with the `RtcMediaTrack` / `RtcMediaStream` seam. Conversion happens only at
  the boundary (facade and public models) with `wrapNativeTrack` / `wrapNativeStream` and `nativeTrackOf` /
  `nativeStreamOf` from the adapter. Contexts store the seam values (`rtcTrack`, `rtcStream`, marked
  `@internal`); a context built from test fakes returns `null` from the native getters but keeps its state
  (`isReady`, `isMuted`).

## 21. Logging

One SDK logger, created from `FishjamClient(debug: bool)`. Messages are prefixed with `[FISHJAM]` and emitted
through `dart:developer`'s `log` only when `debug` is true. The SDK never calls `print`.

## 22. Deviations from the web SDK

| # | Web SDK behavior | This SDK | Why |
|---|---|---|---|
| D1 | `disconnect()` removes listeners before sending `disconnect`, so the event never reaches the server | `disconnect` is sent first (§3.3) | graceful leave |
| D2 | One ended track aborts track restoration; reconnection never completes and the queue is held forever | ended tracks are skipped; `Reconnected` always follows (§6) | liveness |
| D3 | `disableTrackEncoding` emits the "enabled" event | correct event (§11.4) | bug |
| D4 | bandwidth-set event fires twice; encoding-bandwidth event never reaches the app | each once (§11.5) | bug |
| D5 | negotiation spread over several flags and PC listeners; leaked listener; "unstable" check almost never true | one state machine (§8) | correctness |
| D6 | a plain socket close before joining leaves `connect()` pending forever | `connect()` always settles (§3.2) | liveness |
| D7 | target variant stored before validation, inverted validation | validated first (§14.4) | bug |
| D8 | unknown endpoint/track ids throw inside event handling, local state silently diverges | logged and ignored (§7) | robustness |
| D9 | reconnecting emits a spurious `disconnected` | old session torn down silently (§6) | correctness |
| D10 | local-track handlers assume the track exists | unknown ids are `ArgumentError` at the call site (§11) | robustness |
| D11 | `tracksAdded` for the local endpoint flips negotiation state | ignored entirely (§7) | correctness |
| D12 | `connected` emits `peerJoined`/`trackAdded` for endpoints already in the room | delivered in `Joined` only (§14.1) | one source of truth |
| D13 | `room not found` reported as both auth and join error | auth error only (§4) | no duplicates |
| D14 | `peer removed` / `room stopped` / replaced-by-new-client trigger reconnection attempts | terminal (§4) | reconnecting cannot succeed |
| D15 | no socket liveness check | client pings, pong timeout is a retryable loss (§2.1) | detect dead sockets |
| D16 | `ChannelMessage.source` is a placeholder string | the local peer id (§16) | the server ignores it; the id is more useful |
| D17 | metadata `undefined` may be sent as an empty string | always valid JSON (§2.3) | the server drops empty JSON |
| D18 | `tracksPriorityChanged`, `bandwidthEstimationChanged`, `getBandwidthEstimation` exist but are never fed | dropped | dead API |
| D19 | ICE `disconnected` sends `renegotiateTracks` even mid-cycle | deferred until the cycle ends (§8.2) | keeps client and server in step |
| D20 | a failed `replaceTrack` is swallowed; the call succeeds | rolled back, then the call fails with the error (§11.3) | the app learns the media was not replaced |

## 23. Golden fixtures

`test/fixtures/<name>.json`:

```json
{
  "name": "publish_one_track",
  "description": "…",
  "config": {"reconnect": {"addTracksOnReconnect": true}},
  "steps": [
    {"direction": "api", "call": "addTrack", "args": {"kind": "video", "metadata": {"type": "camera", "paused": false}}, "bind": "cam"},
    {"direction": "out", "message": {"peerMediaEvent": {"renegotiateTracks": {}}}},
    {"direction": "in", "message": {"serverMediaEvent": {"offerData": {"tracksTypes": {}}}}}
  ]
}
```

Step kinds (`direction`):

| direction | Fields | Meaning |
|---|---|---|
| `in` | `message` | the server sends this `PeerMessage` (proto3 JSON) |
| `out` | `message` | the client must send a `PeerMessage` matching this (proto3 JSON) next |
| `close` | `code`, `reason` | the server closes the socket |
| `api` | `call`, `args`, optional `bind`, optional `error` | the app calls a public API; `bind` names the returned id; `error` is the expected error type |
| `rtc` | `event`, `args` | the WebRTC layer reports something (`onTrack`, `iceConnectionState`, `connectionState`, `dataChannelState`, `dataChannelMessage`) |
| `expectRtc` | `call`, `args` | the client must have made this WebRTC call (`addTransceiver`, `createDataChannel`, `dataChannelSend`, …) |
| `expect` | `event`, `fields` | the client must have emitted this public event (subset match) |
| `wait` | `ms` | time passes |
| `noOut` | `ms` | time passes and the client must not send anything (ICE candidates excepted) |

The optional top-level `config` holds client settings the test must apply (e.g. `reconnect` with
`maxAttempts`, `initialDelayMs`, `delayMs`, `addTracksOnReconnect`).

Matching rules for `out`, `expectRtc` and `expect`:

- Objects match when every expected key matches (actual may have extra keys with default values; proto3 JSON
  omits defaults). Lists match element-wise and must have equal length.
- `"<any>"` matches any value. `"<sdp>"` matches any non-empty string. `"<sdkVersion>"` matches exactly
  `flutter-<package version>`.
- proto3 JSON omits default values, so an expected default (`0`, `false`, `""`, `[]`, `{}`, `*_UNSPECIFIED`)
  also matches a missing key. Never write `""` for a metadata field: valid JSON is required (§2.3).
- `"${name}"` binds `name` to the actual value on first use and must be equal afterwards. Placeholders are
  allowed in map keys. Bound names are substituted in later `in` messages.
- `out` steps are matched in order against what the client sent; `candidate` messages are skipped by the
  matcher unless the step expects one.
